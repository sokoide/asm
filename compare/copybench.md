# Copy Benchmark: 同じ課題を 9 つの CPU で実装して比較する

`s13_copybench` は全アーキ共通の比較課題。100 バイトのメモリコピーを実装し、宛先の総和（チェックサム）を検証する。

## 課題仕様

- ソース: RAM 上の 100 バイト配列（バイト i = i、0〜99）
- コピー: src → dst に 100 バイト転送
- 検証: 宛先 100 バイトの総和を計算。正解は 0+1+...+99 = 4950 = `0x1356`
- 出力: `COPY OK CHECKSUM=1356`（失敗時 `COPY FAIL CHECKSUM=xxxx`）

## 指標の区別: 命令数 ≠ サイクル数 ≠ 実行時間

クロス CPU 比較では 3 つの物理量を混ぜてはいけない。

- **命令数**: プログラムの書き方（アーキの表現力）を測る指標
- **サイクル数**: その CPU 内部での仕事量。**CPU をまたぐサイクル比較には意味がない**（クロックあたりの回路の違いがあるため）
- **実行時間**: サイクル数 ÷ クロック周波数。異なる CPU の速度を比較できる唯一の指標

以下では、実サイクルが分かる CPU について「基準クロック」を仮定して実行時間も併記する（6502 = 1 MHz、Z80 = 4 MHz、8086 = 5 MHz、68000 = 8 MHz。いずれも代表的な 80 年代実機のクロック）。PPC440 / ARM64 / RISC-V はコア依存のため実行時間では比較しない。

## コピー本体の比較（この比較の核心）

コピー 1 バイトあたりの本体ループ。**命令の多様さ（CISC）と単純さ（RISC）の対比**がここに現れる。

| アーキ | 実装方式 | 1 バイトあたり | 100 バイトのコピー本体 | 実行時間（基準クロック仮定） | 根拠 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 6502 | LDA abs,X / STA abs,X + INX ループ | 16 サイクル | 1599 サイクル | 約 1.60 ms（@1 MHz） | 6502 データシート（sim65 実測で検証可）。ソースに内訳記載 |
| Z80 | LDI + JP PE ループ | 26 T | 2600 T | 約 0.65 ms（@4 MHz） | simz80 T-state 表（go test で保証） |
| Z80 | （参考）LDIR: s101_blockops で実装 | 21 → 16 T/バイト | 2095 T（21×99+16） | 約 0.52 ms（@4 MHz） | 同上 |
| 8086 | REP MOVSB | 17.09 サイクル（9+17n） | 1709 サイクル（セットアップ 14 込み 1723） | 約 0.34 ms（@5 MHz） | Intel 8086 タイミング表（Table 2-21、isa CLI と秘伝の書で照合）。ソースに内訳記載 |
| 80386 | REP MOVSB (ESI/EDI/ECX) | 1 命令 (マイクロコードループ) | サイクル不測定 | — | 386 のブロック転送タイミングは対象外（s13 ソース NOTE 記載）。実行は QEMU TCG でサイクル計測不可 |
| 68000 | MOVE.B (A0)+,(A1)+ + DBRA | 22 サイクル | 2238 サイクル（LEA/MOVE.W 含む） | 約 0.28 ms（@8 MHz） | MC68000 タイミング表。ソースに内訳記載 |
| PPC | LBZ/STB + CTR (bdnz) | 5 命令 | サイクル不測定 | — | スーパースケーラでコア依存のため |
| RISC-V | LBU/SB + ループ | 6 命令 | 同上 | — | 同上 |
| ARM64 | LDRB/STRB (post-index) + ループ | 4 命令 | 同上 | — | 同上 |

読みどころ:

- **8086 の REP MOVSB は 17.09 クロック/バイト**。バスサイクルが 4 クロックで read+write だけで最低 8 クロックのため、これが物理的な下限に近い。CISC のマイクロコードループはループのオーバーヘッドを命令の外に隠せるが、消えるわけではない
- **Z80 の LDIR（16 T/バイト）と 8086 REP MOVSB（17.09 クロック/バイト）はクロック数では僅差**。ただし実行時間では Z80 @4 MHz が 5.25 µs/バイト、8086 @5 MHz が 3.42 µs/バイトと 8086 が有利。「1 命令で書ける強さ」と「クロック当たりの仕事」は別の話で、クロック周波数が速度を決める
- **6502 は abs,X インデックスの読み書きループで 1 バイト 16 サイクル**かかる。ポインタ間接 (zp),Y を使うとさらに重くなる。アドレス空間 64KB を 8 ビットレジスタの組合せで扱う構造的な重さ。@1 MHz では 16 µs/バイトで、他の 3 CPU の数倍の時間がかかる
- **68000 は 22 サイクル/バイトだが @8 MHz** なので実行時間では最速。1980 年代の CPU は「サイクル数が多くてもクロックが高い」傾向にあり、実行時間で見ないと誤解する好例
- **RISC の RISC-V/ARM64/PPC は命令が単純**。1 命令あたりのサイクルはコア設計依存（パイプライン化で 1 バイト 1 サイクル以下になる）なので、この教材では**命令数**で比較しサイクル比較はしない
- **ARM64 の post-index writeback**（`LDRB w3, [x0], #1`）はポインタ更新をロードに統合し、ループ本体が 4 命令で最短

## 計測方針（make cycles と make icount の分け方）

QEMU の実行時間は実機の CPU 性能比較に使えない（TCG はサイクル精度のエミュレーションではない）。`make cycles`（実サイクル/T-state）と `make icount`（実行命令数）を分け、実サイクルが取れない環境では cycles は `unsupported` とだけ表示して代替値を出さない。

1. **実測（正確なサイクルモデルを持つシミュレータ）**: 6502 = sim65/sim65i、Z80 = simz80。`make cycles` で実測できる
2. **データシート計算**: 8086 / 68000。`isa x86_16 MOVS` / 68000 タイミング表に基づき、ソースコメントに命令ごとのサイクル内訳を記載して検証可能にする
3. **命令数のみ（make icount）**: PPC / ARM64 / RISC-V / x86_16 / x86_32。スーパースケーラ・キャッシュ・分岐予測で 1 命令あたりのサイクルがコア設計に依存するため、サイクル比較は意味を持たない
