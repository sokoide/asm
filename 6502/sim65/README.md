# 6502 アセンブラ ワークショップ

cc65 付属のシミュレータ sim65 を使い、12 のシナリオで 6502 アセンブリを段階的に学ぶ。

## 前提条件

| ツール      | 用途                | インストール例                           |
| :---        | :---                | :---                                     |
| cc65 (cl65) | アセンブラ + リンカ | `apt install cc65` / `brew install cc65` |
| sim65       | 6502 シミュレータ   | cc65 に同梱                              |

## ビルドと実行

```bash
# 全シナリオをビルド
make

# 特定のシナリオを実行
make run S=s01_hello

# 掃除
make clean
```

## デバッグ

```bash
# 全命令の実行トレース（前命令との差分行付き）
make trace S=s03_stack

# トレースを less で 1 命令ずつ送って見る（リプレイ型）
make debug S=s03_stack

# 実サイクル数を表示
make cycles S=s03_stack
```

- **make trace**: `sim65 --trace`（1 命令ごとに通番 / 累積サイクル / PC / オペコード / 逆アセンブル / 実行前レジスタ / Flags / SP を表示）に awk スクリプト (`trace-diff.awk`) で変化したレジスタの `BEFORE:` / `AFTER:` / `CHANGE:` 3 行セットを付けて表示する。
- **make debug**: **リプレイ型**。トレースを `$(S).trace` に記録し、less の SPACE/Enter で 1 命令ずつ送って観察する。sim65 に対話ステップ実行はないため、これは実行済みトレースの「再生」であり、実行中のプログラムへのライブ制御ではない点に注意。
- **make cycles**: `sim65 -c` による実サイクル数の表示（正確な値）。

### トレース出力の読み方

トレース行のレジスタ欄は**その命令を実行する前**の値。`trace-diff.awk` は、変化があったレジスタだけ「実行前値 / 実行後値 / 要約」の 3 行セットをその命令の直下に挿入する。

```text
           2             4  0203  9A        txs               A=00 X=FF Y=00 S=00 Flags=Nvdizc    SP=FFFF
        BEFORE: S=00
        AFTER:  S=FF
        CHANGE: S 00→FF
           3             6  0204  A9 C0     lda  #$C0         A=00 X=FF Y=00 S=FF Flags=Nvdizc    SP=FFFF
        BEFORE: A=00
        AFTER:  A=C0
        CHANGE: A 00→C0
           4             8  0206  A2 FF     ldx  #$FF         A=C0 X=FF Y=00 S=FF Flags=Nvdizc    SP=FFFF
           5            10  0208  85 06     sta  $06          A=C0 X=FF Y=00 S=FF Flags=Nvdizc    SP=FFFF
        BEFORE: SP=FFFF
        AFTER:  SP=FFC0
        CHANGE: SP FFFF→FFC0
```

- `BEFORE:` はその命令の実行前値（トレース行のレジスタ欄と同じ値）、`AFTER:` は実行後値（= 次のトレース行のレジスタ欄の値）、`CHANGE:` は old→new の要約。差分が命令の直下に来るため、「どの命令が何を変えたか」が 1 箇所で読める。
- `txs` の `CHANGE: S 00→FF` は TXS が **CPU のハードウェアスタックポインタ S** を設定した結果。`SP=` 欄は変化していない。
- `sta $06` の `CHANGE: SP FFFF→FFC0` は TXS ではなく、cc65 ランタイムのスタートアップがソフトウェアスタックポインタを初期化した結果（ゼロページの `sp` 変数に $FFC0 を書き込む）。
- **`S` と `SP` は別物**: `S` = CPU のハードウェアスタックポインタ（8 ビット。`TXS` / `TSX` / `PHA` / `PLA` / `JSR` / `RTS` が操作し、ハードウェアスタック $0100-$01FF を指す）。`SP` = cc65 ランタイムのソフトウェアスタックポインタ（16 ビット、ゼロページの `sp` 変数。C 関数呼び出しのローカル変数・パラメータ領域で、ランタイムの `pushax` / `popax` などが操作する）。

## sim65i（割り込み対応シミュレータ）

`sim65src/` は cc65 の sim65 ソースをベンダリングしたもので、`make` 時に `sim65i` として自動ビルドされる。cc65 本家の IRQ/NMI 機構（`IRQRequest`/`NMIRequest`）に、メモリマップドトリガ（`$FFCC` = IRQ、`$FFCE` = NMI）を `memory.c` に追加したもの。既存シナリオはシステム sim65 とサイクル数まで同一の挙動を示す（`-c` / `--trace` 対応）。

## 拡張シナリオ

### S13: コピー比較ベンチ（Copy Bench）

**難易度**: ★★★☆☆

全アーキ共通の比較課題。100 バイト（バイト i = i）のメモリコピーを `LDA`/`STA` + absolute,X の素朴なバイトループで行い、宛先 100 バイトの和を 16 ビットチェックサムとして 16 進 4 桁で出力する。

| 学習項目                | 説明                                              |
| :---                    | :---                                              |
| absolute,X ループ       | `LDA src,X` / `STA dst,X` によるバイトコピー      |
| 16 ビットチェックサム   | `ADC sum_lo` + `ADC #0` でキャリ伝播              |
| `CMP` による検証        | 宛先を既知パターン（dst[i] = i）と照合            |
| `print_hex8` × 2        | 16 ビット値を 16 進 4 桁で出力                    |

正解チェックサム: 0+1+...+99 = 4950 = $1356。最終出力は `COPY OK CHECKSUM=1356`（失敗時 `COPY FAIL CHECKSUM=xxxx`）。

コピー部の手計算: LDA abs,X 4 + STA abs,X 5 + INX 2 + CPX # 2 + BNE 3 = 16 サイクル/バイト → 100 バイトで 16×99+15 = 1599 サイクル。

**学習カード**

- **予測**: 上の「手計算」の内訳から、100 バイトコピーの合計サイクルを自分でも計算して予想してから実行する
- **観察**: `make cycles S=s13_copybench` は**プログラム全体**の合計サイクル（15,428）を出す。コピー本体だけの 1,599 は `make trace S=s13_copybench` の累積サイクル列（2 フィールド目）でループ入口と出口の差を取るか、ソースコメントの内訳と照合する。`make trace S=s13_copybench` で `@copy` ループ 1 回転（`lda src_data,x` → `bne`）の累積サイクル差分（隣接行の累積値の差）が 1 バイトあたり 16 サイクルどおりになることを確認する
- **改造**: コピーを `(zp),Y` 間接インデックス（`LDA (ptr),Y` 5 / `STA (ptr),Y` 6 サイクル）に書き換え、1 バイトあたりのサイクルがどう変わるか確認する
- **考察**: 6502 はブロック転送命令を持たず、1 バイトずつ運ぶループを自前で書く方式。Z80 の `LDIR`（1 バイト 21T）や 8086 の `REP MOVSB` との比較は `compare/copybench.md` を参照

### S101: ゼロページ高速アクセス

**難易度**: ★★★★☆

ゼロページは 6502 の「レジスタファイル」。同じ 10 回加算ループを zp アドレッシング版と absolute 版で実装し、結果を出力する。サイクル数の命令ごとの内訳はソースコメントに記載。

| 学習項目          | 説明                                                     |
| :---              | :---                                                     |
| `LDA zp` = 3      | absolute 版 `LDA abs` = 4 より 1 サイクル速い            |
| `STA zp` = 3      | absolute 版 `STA abs` = 4 より 1 サイクル速い            |
| ループ合計        | zp 151 サイクル vs abs 171 サイクル（10 回で +20）      |
| `(zp),Y`          | 間接インデックス 5 サイクル（ページ跨ぎ +1）のポインタ走査 |

`make cycles S=s101_zeropage` で sim65 の正確なサイクル実測が可能。

**学習カード**

- **予測**: `LDA zp` と `LDA abs` はそれぞれ何バイト・何サイクルか。ソースコメントの内訳（15 サイクル/反復 vs 17 サイクル/反復）から 10 回のループの合計差を予想してから実行する
- **観察**: `make trace S=s101_zeropage` で zp 版と abs 版の `LDA` のオペコードバイト数（命令長）の違いを確認し、`make trace S=s101_zeropage` の累積サイクル列（2 フィールド目）で zp ループと abs ループの入口・出口を読み取り、ループ部分だけの実測差（151 vs 171 = 20 サイクル差）を手計算と照合する。`make cycles` が出すのはプログラム全体の合計で、ループ単位の値ではない
- **改造**: ループ回数を 10 回から 100 回に変えて、サイクル差がどう増えるか（1 反復 +2 サイクル）確認する
- **考察**: Zero Page が速い理由は、アドレスが 1 バイトで済み命令フェッチが 1 回少ないため。16 ビットレジスタ (HL) で指す Z80 の `(HL)` 間接（`LD A,(HL)` 7T）と比べるとどうか

### S102: 自己書き換えコード

**難易度**: ★★★★☆

実行中に命令のオペランドを書き換えて挙動を変えるデモ。sim65 は CODE セグメントを RAM から実行するため動作する。6502 にはキャッシュがないため、書き換えた命令は即座に有効になる。

| 学習項目              | 説明                                                     |
| :---                  | :---                                                     |
| `STA self_char+1`     | 即値 `LDA #n` のオペランドバイトを書き換え              |
| コード = データ       | オペランドバイトはコードとデータの両方として機能        |
| `INC self_char+1`     | コードバイトをその場でインクリメント（文字イテレータ）  |
| 前提条件              | ROM 常駐コードでは不可能・キャッシュフラッシュ不要      |

**学習カード**

- **予測**: `sta self_char+1` は何を書き換えているか。次に `self_char` を実行したとき `LDA` がロードする値、そして `INC self_char+1` がコードに与える影響を予想してから実行する
- **観察**: `make trace S=s102_selfmod` で `sta self_char+1` の後に `self_char` を再実行したとき、オペランド書き換えの結果が `lda` 行の直下の `CHANGE: A 41→5A` のような A の変化として現れることを追う
- **改造**: 書き換える値（`#$5A`）を別の文字に変える。`INC` ループの回数を変えて、出力される文字列がどう変わるか確認する
- **考察**: キャッシュを持つ CPU（ARM64、x86 など）では自己書き換えコードは命令キャッシュのフラッシュや実行フェンスが必要。6502 はキャッシュがないため書き換えが即座に有効になるが、コードが RAM 上にある前提で ROM 常駐コードでは不可能

### S103: IRQ & NMI（sim65i 拡張）

**難易度**: ★★★★☆

6502 の 2 本の割り込み入力を実演する。CPU コア自体は cc65 sim65 に IRQ/NMI 機構があるが、トリガする呼び出し元がないため、リポジトリ内ビルド **sim65i**（`sim65src/`、cc65 の sim65 ソースをベンダリングし割り込みトリガ MMIO を追加）を使用する。

| 学習項目             | 説明                                                         |
| :---                 | :---                                                         |
| ベクタ設定           | $FFFE/$FFFF (IRQ)、$FFFA/$FFFB (NMI) へのハンドラ登録        |
| IRQ (maskable)       | I フラグ = 0 のときのみ命令境界で受付（エントリ 7 サイクル） |
| I フラグによるマスク | SEI 中の IRQ は受付されず、CLI 後に配信される                |
| NMI (non-maskable)   | I フラグ = 1 でも受付される（エッジトリガの学習モデル）      |
| RTI                  | P と PC の復帰（6 サイクル）。B=0 がハードウェア割り込みの印 |

トリガは MMIO 書き込み: `$FFCC` に書くと IRQ パルス、`$FFCE` に書くと NMI パルス（値は無視）。周辺機器が割り込みラインを上げる様子の教育用モデルで、簡略化としてリクエストは受付までラッチされる（実機のレベルトリガ IRQ ではデバイスがラインを下ろすと要求は消失する）。

実行は `make run S=s103_irq_nmi`（sim65i を自動使用）。`make cycles S=s103_irq_nmi` で割り込みエントリ 7 サイクル + RTI 6 サイクルを含む合計が得られる。

**学習カード**

- **予測**: 割り込みエントリで CPU は PC（2 バイト）と P（1 バイト）をスタックに積む。S はいくつ減るか。SEI 中に `$FFCC` をトリガした IRQ はいつ配信されるか、予想してから実行する
- **観察**: `make trace S=s103_irq_nmi`（このシナリオは debug / trace / cycles とも sim65i を使用）で Demo 1 の `sta $FFCC` の後の `*** IRQ ***` 行の直下 `CHANGE: S FD→FA`（3 バイト push、エントリ 7 サイクル）と、ハンドラ末尾 `rti` の `CHANGE: S FA→FD`（復帰）を追う
- **改造**: Demo 2 の `sei` を `cli` に変えて即座に配信されることを確認する。またはハンドラ内で push するレジスタを増減させ、S の増減と RTI 後の復元をトレースで追う
- **考察**: 実機の IRQ はレベルトリガでデバイスがラインを下ろすと要求は消失するが、sim65i は受付までラッチする簡略化（シナリオヘッダのコメント参照）。Z80 の `INT` / `NMI` との比較は `z80/sim` の `s102_interrupts` を参照

## I/O ルーチン

sim65 は実機の ROM BIOS を持たず、cc65 の **sim6502 ターゲット用 C ランタイムライブラリ**（cc65 パッケージ同梱の `lib/sim6502.lib`、リンカ設定 `cfg/sim6502.cfg`）とリンクして動作する。これらの関数はホスト OS の標準入出力・ファイルシステムをエミュレートする **paravirtualized** な環境で実現されており、実機のハードウェアレジスタを直接叩くわけではない。

**cc65 の 6502 呼出規約**: アセンブリから関数を呼ぶとき、右端（最後）の引数はレジスタで渡す（1 バイト値 → `A`、2 バイト値・ポインタ → `A`=下位 / `X`=上位）。残りの引数はソフトウェアスタックに積む。返り値は `A`（8-bit）または `A/X`（16-bit、`A`=下位）。呼び出しは `jsr <func>`。

**主な関数**:

| 関数       | 入力                          | 返り値                    | 意味                                        | 教材使用 |
| :---       | :---                          | :---                      | :---                                        | :---     |
| `_putchar` | `A` = 文字                    | `A` = 出力文字（通常無視）| 1 文字を stdout に出力                      | 高       |
| `_getchar` | なし                          | `A/X` = 入力文字（EOF=-1）| 1 文字を stdin からブロッキング入力         | 中       |
| `_puts`    | `A/X` = ヌル終端文字列アドレス | `A/X` = 最後の文字        | ヌル終端文字列 + 改行を出力                 | 低       |
| `_exit`    | 終了コード（C 規約でスタック渡し）| 戻らない                | プログラムを終了（sim65 プロセス終了）      | 未使用   |
| `_read`    | fd/buf/count（C 規約）        | `A/X` = 読込バイト数      | ファイル/ストリームから読込                 | 未使用   |
| `_write`   | fd/buf/count（C 規約）        | `A/X` = 書込バイト数      | ファイル/ストリームへ書込                   | 未使用   |

**終了の仕組み**: 教材は `_exit` を明示的に呼ばず、エントリの `_main` から `rts` で cc65 のスタートアップルーチンへ復帰する。スタートアップが `_exit` を呼び出し、sim65 がプログラムを終了する。

**注意**: `_putchar` / `_puts` / `_getchar` は X, Y レジスタを破壊する。ループカウンタとして使用している場合は、呼び出しの前後で必ず退避・復元すること。ゼロページ上の変数も破壊される可能性があるため、固定ゼロページアドレス（`$F0` など高アドレス）を使用するか、ハードウェアスタックで退避すること。

**定義元**: cc65 `lib/sim6502.lib`（関数モジュール `putchar.o` / `getchar.o` / `puts.o` 等）。実機 ROM ではなく sim65 ホストがエミュレートする。
