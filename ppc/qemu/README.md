# PowerPC アセンブラ ワークショップ

PowerPC ベアメタル アセンブラの基礎から応用まで、12 のシナリオで段階的に学ぶ。

## 前提条件

| ツール | 用途                 | インストール例                |
| :---   | :---                 | :---                          |
| Clang  | PowerPC アセンブラ   | `apt install clang`           |
| LLD    | PowerPC リンカ       | `apt install lld`             |
| QEMU   | PowerPC エミュレータ | `apt install qemu-system-ppc` |

## ビルドと実行

```bash
# 全シナリオをビルド
make

# 特定のシナリオを QEMU で実行
make run S=s01_hello

# 全シナリオを順に実行
make runall

# 逆アセンブル
make dump S=s01_hello

# 掃除
make clean
```

## デバッグ

```bash
# QEMU を -S -gdb tcp:127.0.0.1:1234 で起動し gdb を接続（ステップ実行）
make debug S=s01_hello

# 命令ごとの逆アセンブル + CPU 状態を s01_hello.trace に記録して less で閲覧
make trace S=s01_hello

# 実行命令数を集計 (実サイクルは make cycles が unsupported を表示)
make icount S=s01_hello
```

`make debug` では gdb の `si`（1 命令ステップ）/ `c`（続行）/ `b *ADDR`（ブレークポイント）/ `info registers` / `x/5i $pc` で観察する（gdb が必要: `brew install gdb`、ポートは `GDB_PORT` で変更可）。UART 出力はステップ実行の進行に応じて同じターミナルに表示される。`make cycles` は QEMU TCG がサイクル精度のエミュレーションではないため `unsupported` を表示し、実行命令数は `make icount` で計測する。

### S13: Copy Benchmark（共通課題: 100 バイトコピー）

**難易度**: ★★★☆☆

全アーキ共通の比較課題。100 バイトのメモリコピーを行い、宛先の総和（チェックサム `0x1356`）を検証する。詳細と他アーキとの比較は `compare/copybench.md` を参照。

| 学習項目       | 説明                                        |
| :---           | :---                                        |
| CTR ループ     | `mtctr` / `bdnz` によるカウンタループ       |
| ブロック転送   | PPC に専用命令は無く LBZ/STB の繰り返し     |
| チェックサム   | 宛先 100 バイトの総和でコピーを検証         |

**学習カード（予測 → 観察 → 改造 → 考察）**:

- **STEP 1 予測**: コピー本体 `.Lcopy` は `lbz` → `stb` → `addi` × 2 → `bdnz` の 5 命令 × 100 回。ここにチェックサムループと出力ルーチンが加わる。`make icount S=s13_copybench` の総命令数はおよそ何命令になるか予測してから実行して比べる。
- **STEP 2 観察**: `make trace S=s13_copybench` で `.Lcopy` が 5 命令の組み合わせを 100 回繰り返すことを確認する。`bdnz` が CTR を減らすだけで CR を汚さない点（ループ内で `cmpwi` を使っても干渉しない）もトレースで見る。
- **STEP 3 改造**: ループ本体を `lwz`/`stw` 4 バイト転送に差し替えて反復 25 回にしたとき、icount がどれだけ減るか予測してから測る。100 が 4 で割り切れない場合の端数処理も含めて考える。
- **STEP 4 考察**: Z80 `LDIR` は 1 命令/バイト、x86 `REP MOVSB` も 1 命令で複数バイト、PPC は 5 命令/バイト。`compare/copybench.md` を参照し、「命令数の多さ」と「クロック当たりの仕事」を区別して比較する練習をする。

### S101: CR とリンクレジスタ

**難易度**: ★★★★☆

PowerPC 特有の「命令は固定で、状態は CR とリンクレジスタに分離する」設計。比較の対象フィールド指定、CR 論理命令による条件合成、mfcr/mtcrf、bdnz ループ中の bl を学ぶ。

| 学習項目            | 説明                                                       |
| :---                | :---                                                       |
| CR フィールド指定   | `cmpwi cr1, ...` で CR0 を壊さず比較                       |
| CR 論理命令         | `cror` などで複数フィールドの条件をビット単位で合成        |
| mfcr / mtcrf        | CR 全体の読み書き（コンテキスト保存の基礎）                |
| bdnz                | LR を壊さないカウンタ分岐（ループ中に bl しても安全）      |

**各デモの観察ポイント**: ソースには 6 つのデモが直列に並ぶ。各デモの入口に `demo1_cr0_compare` 等のラベルを付けてあるので、`make debug` で目的のデモまで一気に進んでからステップ実行すると観察しやすい。

| デモ | ラベル | break アドレス | 観察ポイント |
| :--- | :--- | :--- | :--- |
| 1 | `demo1_cr0_compare` | `0x8` | `cmpwi` 後の CR0（`cr 0x2` = EQ）。`beq` が CR0.EQ を見て分岐する |
| 2 | `demo2_cr_field_compare` | `0x38` | 2 連続 `cmpwi` 後の CR = `0x28000000`（CR0=EQ, CR1=LT）。CR1 比較後も CR0.EQ が無傷で `beq` が通る |
| 3 | `demo3_cr_logic` | `0x88` | `cror 2,2,6` で CR0.EQ (bit 2) に CR1.EQ (bit 6) を OR して EQ 分岐が通る |
| 4 | `demo4_mfcr` | `0xc0` | `mfcr` の戻り値 `0x28000000` が CR のビットマップそのもの |
| 5 | `demo5_mtcrf` | `0xe8` | `mtcrf 0x80` で CR0 <- 0b0100 (GT) に書き換わり `bgt` が通る |
| 6 | `demo6_bdnz_bl` | `0x118` | ループ中の `bl ten` で LR が上書きされても `bdnz` が正常に回る（3 回 × 10 = 0x1E を出力） |

アドレスは `make dump S=s101_cr_lr`（`llvm-objdump -t`）で確認できる（`demo1_cr0_compare` = 0x00000008 等）。

**学習カード（予測 → 観察 → 改造 → 考察）**:

- **STEP 1 予測**: Demo 2 の `cmpwi`（CR0）と `cmpwi cr1` を連続実行したとき、gdb の `info registers` で見える CR は何になるか（EQ は上位か下位のフィールドか）。Demo 3 の `cror 2,2,6` の 3 つのオペランドがそれぞれどのビットを指すか予測する。
- **STEP 2 観察**: `make debug S=s101_cr_lr` を起動し、上の表の break アドレス（例: `b *0x38`）で Demo 2 に進み、`cmpwi cr1` 実行前後で `info registers` の `cr` の値を比べる。Demo 4 では `mfcr` が返す値が Demo 2 の CR と同じ形式であることを確認する。
- **STEP 3 改造**: Demo 3 の `cror 2,2,6` を `crand 2,2,6` に変えると分岐が通らなくなるはず（CR0.EQ=0 AND CR1.EQ=1）。予測してから実行する。Demo 4 の `cmpwi cr1, 99` を `cmpwi cr1, 7` に変えると `mfcr` の戻り値がどう変わるかも予測してから観察する。
- **STEP 4 考察**: x86/Z80 は FLAGS 1 個なので「比較結果の退避」は `pushfq` 等が必須、ARM64 も NZCV 1 個。PPC は 8 フィールドの CR で比較対象を指定でき、コンパイラが比較を再順序付けしやすい設計。`ppc/CPU.md` の CR 節と、S102（例外時の MSR 退避）との対比も読む。

### S102: 例外処理（Book E IVPR/IVOR）

**難易度**: ★★★★☆

PPC440 (Book E) の例外処理。ベクタは IVPR（64KB 境界）+ IVORn の合成、例外状態は SRR0/SRR1 のレジスタ渡し、復帰は rfi。`tw` トラップと `sc` システムコールを実演する。

| 学習項目        | 説明                                                          |
| :---            | :---                                                          |
| IVPR / IVOR     | 例外ベクタの合成（`mtspr` で設定、ハンドラは 0x01000100 系）  |
| tw トラップ     | SRR0 はトラップ命令自身を指すためハンドラで +4 して復帰       |
| sc              | システムコール（SRR0 は既に次の命令）                         |
| SRR0 / SRR1     | 例外時の PC と MSR の自動保存（x86 のスタックフレーム対比）   |

観察: `make trace S=s102_exceptions` で例外突入時の NIP と MSR の変化が追える。

**学習カード（予測 → 観察 → 改造 → 考察）**:

- **STEP 1 予測**: `tw` トラップで SRR0 は tw 命令自身を指す。ハンドラの `SRR0 += 4` を外したら rfi 復帰後どうなるか。一方 `sc` は SRR0 が既に次の命令 — 両者の違いを先に予測する。
- **STEP 2 観察**: `make trace S=s102_exceptions` で、`tw` 実行時に NIP がハンドラ（IVPR+IVOR6 = 0x01000100）へジャンプすること、ハンドラ内の `SRR0 += 4` で NIP が +4 されること、`rfi` で元の流れに戻ることを追う。`make icount S=s102_exceptions` で例外 2 回を含む総命令数も確認する。
- **STEP 3 改造**: tw 側ハンドラの `SRR0 += 4`（スキップ）をコメントアウトして `make run` すると、「pre」表示の無限ループ（tw の再実行）になることを予測してから確認する。戻すのを忘れずに。
- **STEP 4 考察**: x86 `INT n` / m68k `TRAP #n` / ARM64 `SVC` はいずれも例外時 PC が「次の命令」を指すが、PPC の `tw` は「例外を起こした命令自身」を指す（fault 型）。S102 の SRR0 と ARM64 S102 の ELR（`s102_svc`、+4 スキップ不要）を対比する。

## ハードウェア情報

### QEMU bamboo マシン

- **CPU**: PowerPC 405GP
- **メモリ**: 64MB RAM
- **UART**: 16550 compatible at 0xEF600300
- **タイマー**: Time Base register（特殊レジスタ）

### 16550 UART レジスタ

| オフセット | 名称 | 方向 | 説明                                    |
| :---       | :--- | :--- | :---                                    |
| 0x00       | RBR  | R    | Receiver Buffer Register（受信データ）   |
| 0x00       | THR  | W    | Transmit Holding Register（送信データ） |
| 0x05       | LSR  | R    | Line Status Register（状態レジスタ）     |

**LSR ビットフラグ**:

| ビット | 名称 | 説明                                          |
| :---   | :--- | :---                                          |
| bit 0  | DR   | Data Ready — 受信データあり（1=受信完了）      |
| bit 5  | THRE | Transmitter Holding Register Empty — 送信可能（1=書き込み可） |

**受信手順**: LSR bit 0（DR）が 1 になるまでポーリング → RBR（0x00）から 1 バイト読み取り

**送信手順**: LSR bit 5（THRE）が 1 になるまでポーリング → THR（0x00）へ 1 バイト書き込み

### ツールチェーン

| コンポーネント | コマンド                          | 役割                     |
| :---           | :---                              | :---                     |
| アセンブラ     | `clang --target=powerpc-none-elf` | アセンブリソースをオブジェクトに変換 |
| リンカ         | `ld.lld`                          | オブジェクトをELFバイナリに結合 |
| エミュレータ   | `qemu-system-ppc -machine bamboo -nographic` | ベアメタル実行 |

### アセンブラ疑似命令

| 疑似命令   | 説明                                | 使用例                    |
| :---       | :---                                | :---                      |
| `.section` | セクション切り替え（.text/.data/.rodata/.bss） | `.section .text`          |
| `.global`  | シンボルを外部公開                  | `.global _start`          |
| `.asciz`   | null終端文字列を定義                | `msg: .asciz "Hello\n"`   |
| `.byte`    | 1バイトデータを配置                 | `.byte 0x0A`              |
| `.word`    | 4バイトデータを配置                 | `.word 0xDEADBEEF`        |
| `.space`   | 領域を確保（ゼロ埋め）              | `.space 256`              |
| `.align`   | アドレスをアライメント              | `.align 2`（4バイト境界） |
| `.dword`   | 8バイトデータを配置                 | `.dword 0x123456789ABCDEF0` |

### Makefile ターゲット

| ターゲット      | 使用例                   | 説明                             |
| :---            | :---                     | :---                             |
| `make`          | `make`                   | 全シナリオ（s01〜s12）を一括ビルド |
| `make run`      | `make run S=s01_hello`   | 指定シナリオを QEMU で実行        |
| `make runall`   | `make runall`            | 全シナリオを順次実行              |
| `make dump`     | `make dump S=s01_hello`  | 指定シナリオの逆アセンブル出力    |
| `make clean`    | `make clean`             | ビルド生成物を削除                |

### リンカスクリプト（linker.ld）

| 項目          | 値                                |
| :---          | :---                              |
| エントリポイント | `_start`                          |
| ロードアドレス   | `0x00000000`                      |
| セクション構成   | `.text` → `.rodata` → `.data` → `.bss` |

### 終了方法

PowerPC ベアメタルでは標準的な終了処理が存在しない。QEMU は無限ループで停止を検出できないため、`--foreground 1` オプションで 1 秒後にタイムアウトさせる。

## I/O ルーチン

PowerPC ベアメタル（QEMU `bamboo` マシン）では、**プログラムが呼び出せる外部 I/O コール（BIOS・システムコール・セミホスティング・終了デバイス等）は提供されない**。すべての入出力と終了はハードウェアレジスタ（MMIO）の直接操作か、CPU の停止（無限ループ）による。

| 操作         | 方法                         | 参照先                                                         |
| :---         | :---                         | :---                                                           |
| 文字出力     | 16550 UART MMIO（`0xEF600300`） | [16550 UART レジスタ](#16550-uart-レジスタ) の THR 書き込み |
| 文字入力     | 16550 UART MMIO              | 同上の RBR / LSR ポーリング                                     |
| 時刻取得     | Time Base レジスタ（SPR）    | S08 を参照                                                     |
| プログラム終了 | 無限ループ + QEMU タイムアウト | [終了方法](#終了方法)                                        |

**他アーキテクチャとの対比**: ARM64（semihosting）、RISC-V（SiFive test device）、x86（BIOS 割り込み）、6502（cc65 ランタイム）、Z80（CP/M BDOS）のように、QEMU・ROM・OS が提供する終了デバイスやシステムコールは **`bamboo` マシンでは利用できない**。これは教材が選んだ QEMU マシン設定の制約であり、PowerPC というアーキテクチャ自体の制限ではない（他の PPC マシン・実機環境では Open Firmware 等が提供されることがある）。

**定義元**: 該当なし（外部コール ABI は存在しない）。I/O は 16550 UART の MMIO レジスタ仕様に従う。

## トラブルシューティング

### QEMU が起動しない

```bash
# 必要なツールがインストールされているか確認
which clang ld.lld qemu-system-ppc
# すべてのパスが表示されれば OK
```

- `clang` が見つからない → `apt install clang`（macOS では Xcode Command Line Tools）
- `ld.lld` が見つからない → `apt install lld`
- `qemu-system-ppc` が見つからない → `apt install qemu-system-ppc`（macOS では `brew install qemu`）

### ビルドエラーが発生する

`--target=powerpc-none-elf` が正しく指定されているか確認する。Makefile 内の `ASFLAGS` をチェック:

```makefile
ASFLAGS = --target=powerpc-none-elf -c
```

リンカスクリプト `linker.ld` がカレントディレクトリに存在することを確認。ない場合は `make clean` を実行してから再ビルドする。

### UART が動作しない（文字が表示されない）

1. **アドレス確認**: UART のベースアドレスが `0xEF600300` であることを確認
2. **マシンタイプ確認**: QEMU 起動時に `-machine bamboo` フラグが指定されているかチェック
3. **LSR ポーリング**: 送信前に必ず LSR bit 5（THRE）が 1 になるまでポーリングしているか確認
4. **レジスタ幅**: `STB`（Store Byte）命令で 1 バイト書き込みを行っているか確認。`STW`（Store Word）を使うと隣接レジスタを破壊する可能性がある

## 次のステップ
